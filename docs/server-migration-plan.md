# Sakkuをローカル環境からクラウドへ移す手順

作成日: 2026-10-14。移行の実行書と事前タスク。管理先は [Issue #5](https://github.com/MasakiAijima/sakku/issues/5)。今回の作業は計画とIssue更新であり、環境作成、データ転送、デプロイは未実施。

## 移行の前提を確認する

過去のチャット「クラウド構成とコスト検討」の2026-10-11の利用者発言は「初期的にはアクセスはなく、個人利用の想定」と「将来的には、書いたものを誰もが自由に再利用できるようにしたいので、クラウド化はしたいと思います」。チャットIDは `6acb3aac-c43c-83ee-8ce5-ac0d3e532ca9`。クラウドを記録の正式な保存先とし、作品公開・再利用を後から拡張する計画にする。

同チャットの回答では Workers＋Supabase PostgreSQL・Auth・Storage、Expo、OpenAI を提案している。これは提案であり、技術採用の利用者承認とは区別する。現在のコードは Vinext・React＋Workers・D1・R2、GroqによるHaiku生成で、最初の実機対象は #1 に記録された iPhone Safari のWeb版。SupabaseへのDB変更、Expo化、AIモデル変更を初回配置の必須工程にはしない。

初回移行は既存 Workers・D1・R2 を維持する案を推奨する。#1 で Sites のホスティングを使うか独立 Cloudflare に配置するかと認証を決め、#4 で保存先を正式に決める。Supabaseを採用する場合は、SQL、保存処理、認証、画像アクセス、利用枠予約を置き換える移行計画を別途作り、このD1用手順を流用しない。過去の無料枠・月額試算は再利用せず、選定時に現在の料金、休止条件、バックアップ条件を再確認する。

### 移行元コードを固定する

調査時のローカルHEADは `8b541a7` で、未コミット成果物が残る。これを直接配布しない。調査時のリモートmainは `ef89682441a023988769effec8dc163f8b6c543b`、PR #27・#28を含む。

PR #29 は `codex/seasonal-acceptance`、#31 は `codex/issue6-8-input`、#32 は `codex/issue30-worker-bindings` へマージ済み。`main...codex/issue4-photo-storage` の比較は ahead 5 / behind 1。子ブランチへのマージ完了をmainへの反映完了と扱わない。#29の入力・言語、#31のbinding重複修正、#32の写真保護をmainへ統合し、統合後のSHAとCI結果を移行記録に残す。統合作業では既存変更との重複を照合する。

検証はNode.js 24とロックされたpnpmを使い、リポジトリのCIにある検証を再現する。`pnpm start` はビルド済みWorkerをローカル保存先で動かすコマンドであり、本番起動・デプロイコマンドではない。#30のローカル起動試験は本番認証の試験とは区別する。

### 認証と本人IDを先に整える

現在の `app/chatgpt-auth.ts` は `oai-authenticated-user-id` とメールのヘッダーを信頼する。`build/sites-vite-plugin.ts` のヘッダー除去と固定ユーザー注入は開発用。`build/sites-worker.ts` は受信リクエストをハンドラーへ渡す。

Sitesを維持する場合は、ホストの認証と本人情報の注入が実配置先で成立することを確認する。独立Cloudflareの場合は、署名を検証する認証実装または信頼できる認証プロキシが必要。プロキシを使う場合も、Workerへの直通URLを保護し、外部からの本人ヘッダーを信頼しない。未認証、期限切れ、失効、偽装ヘッダー、別人のIDで、記録・設定・写真・生成履歴の取得と変更が拒否されることを確認する。

固定開発ユーザー `local_seedy` を正式アカウントへ一括で自動対応させない。移行対象の所有者と引継ぎ先を本人確認し、対応表を私的な移行記録として保存する。旧Sitesの記録がある場合も別の移行元として棚卸しし、メール一致だけで統合しない。

### 配置設定と費用を確定する

現 `wrangler.jsonc` のD1 IDは仮値で、R2名もローカル向け。#31の重複修正を取り込んだ後、ローカル・検証・本番それぞれの設定元とビルド時の選択方法を実装する。生成設定 `dist/server/wrangler.json` のWorker名、D1 ID、R2名、静的ファイル、秘密情報参照を照合する。どの環境向けにビルドしたかを配置記録へ残す。

AIキーは秘密情報管理へ登録し、`.env.local` をアップロードしない。現在のGroqモデル設定と回数・トークン上限を明示する。有料モードは勝手に有効にしない。翻訳は現在 `lib/haiku-translation.ts` から直接providerへ通信し、生成ジョブの利用枠予約を通らないため #8 で制御を追加する。

契約プラン、月額上限、D1使用量、R2容量・操作数、Worker使用量、AI使用量、GitHub Actions、バックアップ先の費用と確認方法を記録する。無料枠超過時の挙動と停止方法も決める。AIキー未設定、D1/R2不足、AI失敗の検証ができるHTTPS環境を本番と分けて用意する。

### データと画像の移行をリハーサルする

1. ローカルDB・R2、旧Sitesのクラウドデータの有無を確認する。個人記録、下書き、設定、写真管理情報、生成履歴、使用量予約を棚卸しする。開発試験データを区別し、引継ぎ対象を決める。空で始める場合もその判断を記録し、元データを保存する。
2. DBと画像の整合したバックアップを作るため移行元の書込みを止める。DB書出し、画像全実体、所有者・参照・状態・件数・サイズ・SHA-256の目録を私的な保存先へ作る。`.wrangler` の内部ディレクトリをそのままクラウドR2へ転送しない。
3. 空の検証環境へ復元する。全スキーマdumpを使う方式と、マイグレーション済みDBへデータのみ取り込む方式のどちらかを選ぶ。二重にスキーマを作らず、既存表を消すdumpを既存本番へ流さない。適用済みマイグレーションも照合する。
4. 所有者IDを承認済み対応表で変換する。記録ID、日付、版、再送キー、生成ジョブ参照、写真キーを保持する。新しい認証IDで既存記録を取得できることを確認する。利用量予約と処理中ジョブを単純に初期化せず、結果不明の外部呼出しの再送を防ぐ。
5. 写真のR2実体とDBの参照を突き合わせる。移行を再実行しても上書き・重複が発生しない方法を用意する。参照先がない画像、共通キーを参照する旧写真、uploading・delete_pendingなどの途中状態を報告し、結果不明の写真を自動で消さない。
6. 件数、内容、関連参照、画像ハッシュを比較し、別アカウントからのアクセス拒否と本人による再表示を確認する。元のバックアップからもう一度別の空環境へ復元できることを記録する。

D1だけの復旧ではR2画像が戻らない。Workerの旧版への切戻しでもDB・R2・外部AIへの呼出しは巻き戻らない。コード、スキーマ、データ、画像、季節素材の版ごとに復旧方法を記録する。

### 公開する素材を固定する

季節素材は #19 の承認済み `public/seasonal-assets/releases/c-v2/` とmanifest、`current.json` を使う。季節素材のR2化は初回移行の必須条件にしない。公開素材と本人の写真は別のアクセス条件で配布する。承認版と復旧に必要な版を保持し、試作レビュー画面・制作途中データを配布するかを決める。原本はGit履歴で保持する。

ローカルpublicの棚卸しは1,635ファイル、133,883,882 bytes、最大1,577,636 bytes。実配置のファイルは統合後の生成物で再集計する。Cloudflareの公式資料では静的ファイルはFree 20,000件、Paid 100,000件、単一25 MiBまで。これとは別にWorker本体の圧縮サイズ・CPU・メモリ上限をdry-runと実環境で確認する。[静的ファイル上限の公式変更記録](https://developers.cloudflare.com/changelog/post/2025-09-02-increased-static-asset-limits/)、[実行基盤の上限](https://developers.cloudflare.com/workers/platform/limits/)。

Service Workerは公開季節素材だけを保存し、認証済みHTML、個人記録API、本人写真をキャッシュしない。HTTPSで全72候の表示、版切替、オフライン、年境界を確認する。公開・再利用機能は後続工程とし、初回配置の記録・情景・写真は本人だけに公開する。将来の公開範囲と再利用許諾は別の属性として設計し、今回の移行で自動公開しない。

## 検証環境へ配置する

以下は独立Cloudflareを選んだ場合のコマンド形。`<...>` は決定済み値へ置換する。設定ファイルは事前タスクで作るため、現時点ではこのまま実行しない。Sitesを選んだ場合は、その配置手順と認証・binding注入の手順を確定して置き換える。

1. 運用アカウントで検証用Worker、D1、私的R2を用意し、環境設定へ登録する。AIキーはその環境のsecretとして登録する。
2. 固定SHAから検証環境用の配布物をビルドする。`pnpm exec wrangler deploy --dry-run --config <検証用に生成したWorker設定>` で配布物とbindingを確認する。
3. 空の検証D1へ `pnpm exec wrangler d1 migrations apply DB --remote --config <検証用D1設定>` を適用する。前節で全スキーマdump方式を選んだ場合は、空DBへの復元順を先に確定する。
4. `pnpm exec wrangler deploy --config <検証用に生成したWorker設定>` で配置する。URL、Worker版、ソースSHA、D1 ID、R2名、暦版、素材版を記録する。
5. 移行データのリハーサルと、実認証・実保存・実AIの一連操作を通す。CIのAPI固定応答による画面試験だけで合格にしない。
6. iPhone Safariで再ログイン、写真選択、生成、保存、読み返し、画面回転、復帰、オフライン、VoiceOverを確認する。#14〜#16の実機残条件と最終目視承認を同じ記録へ紐づける。

D1コマンドは [Wrangler D1公式資料](https://developers.cloudflare.com/workers/wrangler/commands/d1/)、書出し・取込みは [D1公式移行手順](https://developers.cloudflare.com/d1/best-practices/import-export-data/) に合わせる。`--local` と `--remote`、設定と対象IDを毎回明示して確認する。

## 本番へ切り替える

1. 検証結果、未解決事項、費用上限、バックアップと復旧記録を #5 へまとめる。配置責任者が本番切替を判断する。
2. 本番用の独立したリソース・秘密情報へ同じ検証済みSHAを配置する。環境差だけを確認し、本番で未検証のコード変更を加えない。新規空DBは適用後、非公開で試験する。既存本番DBがある場合は変更前バックアップと互換性を確認する。
3. 移行元の書込みを止め、最終バックアップと検証済み移行処理を実行する。移行先の本人アクセス、件数・ハッシュ一致、参照と未完了状態を照合する。照合が失敗したら公開せず復旧する。
4. HTTPS URLまたはルーティングを切り替え、移行先だけで書込みを開始する。再ログイン、1件の記録保存・写真再表示・生成上限を実アカウントで確認する。旧環境のデータと秘密情報をすぐに削除しない。
5. 監視時間と責任者を決め、認証失敗、5xx、保存失敗、画像欠損、利用量を確認する。問題時は書込みを止め、切替後に増えたデータを退避してから復旧手順を実行する。旧環境へ戻す場合も新規記録の欠落を防ぐ。
6. 公開URLと出所ページが確定した公開時に #21 の提供者連絡を行う。限定検証環境と一般公開の実施時点を区別する。今回の計画作業ではメールを送信しない。

## 完了を判断する

- 再ログイン・別端末でも本人の記録、設定、写真、生成履歴が残り、他人は取得・変更できない。
- 未認証、偽装ヘッダー、開発ユーザー、失効済み認証はAPIを利用できない。
- 生成と翻訳が利用量・費用上限で止まり、失敗・再送・競合で記録の消失や重複課金を招かない。
- DBと写真のバックアップから別環境へ復元でき、切替後の新規記録を保持して復旧できる。
- iPhone実機と最終目視承認の記録があり、移行前タスクに重大な未完了がない。
- #5 に本番URL、ソースSHA、環境、端末・OS、実施日時、結果、復旧手順を残す。

この順序は pstack の Sequence work into verifiable units に従い、コード確定、認証、復元、検証配置、本番切替ごとに合格条件を設けた。Prove It Works に従い、Issue更新はGitHub本文を読み戻して確認し、移行完了は実認証と実保存・復元を確認してから判断する。
